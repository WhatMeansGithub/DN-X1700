# DN-X1600 port of the USB fixes

Status 2026-11-06: **patch data built and checked in software; NOT flashed on any X1600.** Needs a volunteer with a unit.

Legend: [C] = confirmed in the firmware image (code/data), [H] = hypothesis. Nothing here is confirmed on X1600 hardware yet.
The X1700 side of every fix is confirmed on the real unit (see `usb.md`).

## Image
- Denon's `firmware-dnx1600-v2000.zip` contains `X1600FW.BIN`, 2 MiB, sha256
  `befd35c43411b39e796656f12aa850badee49d677522ce5f7a5db504e346c120`. Kept locally in `firmware/original/` (never committed).
- [C] Same code base as the X1700: same boot code layout, same app mapping (flash `0x10000..` ↔ RAM `0x0C000000..`, from the boot
  code's copy literals), same service monitor ("Hello !!! (DN-X1600 monitor)"), same updater. App ends at flash `0xCB350`.
- [C] USB ID `154E:500E` (X1700: `154E:500A`). Linux carries a quirk for this ID that ignores the clock source and hard-codes
  48 kHz because "switching rates via software is currently not working". That matches the bug patch 002 fixes.

## Updater and checksum [C]
- Reads `A:\X1600FW.BIN` from the USB stick (load/verify routine at RAM `0x0C039598`), in **2 x 1 MiB** (X1700: 4 x 1 MiB).
- Same integrity rule: the sum of all little-endian 32-bit words of the image must be `0xFFFFFFFF` (`cmp/eq #-1`). The last
  word (flash `0x1FFFFC`) balances it. `tools/checksum.py` handles both sizes.
- Same flow as the X1700 updater (chip erase, program, verify, "Update error"), so a normal reflash from a stick is the
  recovery for a bad app. [H] As on the X1700, a power cut during the update needs an external flash programmer (for the X1600's own chip, see below).

## Flash chip [C]
- The X1600 updater (RAM `0x0C0399B0..`) reads the flash autoselect device ID and proceeds only if it is **`0x2249` or `0x22C4`**
  (otherwise "Unknown flash chip ID"). The X1700's updater expects `0x22F9` (EN29LV320AB, 4 MB). [C]
- [C] Denon's DN-X1600 service manual (replacement table, "Version upgrade procedure of firmware") lists the flash ROM as
  **IC103 = EN29LV160BB-70TIP** on the MAIN board, and names `X1600FW.BIN` as its software. The Eon EN29LV160 datasheet gives device ID
  `0x2249` for the bottom-boot and `0x22C4` for the top-boot version, 16 Mbit (2M x8 / 1M x16), 48-pin TSOP option (the `T` in `-70TIP`),
  which matches the updater's two accepted IDs and the 2 MiB image. The X1700's IC103 is the 4 MB EN29LV320AB, same reference, different part.
- Consequence: the X1700 recovery notes (EN29LV320AB, TSOP48) do not apply to the X1600 as written. The package is the same, the chip
  type is not: a programmer needs the EN29LV160 setting. [H] The updater probably erases the whole chip as on the X1700; not checked.

## Patch 001 (descriptors) [C]
- The 385-byte configuration descriptor (flash `0xCB0E8`) is **byte-identical** to the X1700's (flash `0xD36A0`).
- Same three bytes at the same descriptor offsets: `0xCB0F5` (IAD class FF→01), `0xCB174` and `0xCB1AB` (AS_GENERAL bmControls 05→00).
- The runtime rewrite at USB init (RAM `0x0C03BEE0`, X1700 `0x0C042F58`) is instruction-for-instruction identical: in MAC mode it
  sets config+13 = 0x01 and the endpoint sync type (config+161, +216) to 0x0D, else 0xFF / 0x09. Its descriptor pointer
  (`0x0C0BB26C`) points at the X1600's descriptor. So, as on the X1700, **macOS needs Utility PC/MAC = MAC** and a power cycle.

## Patch 002 (clock answers) [C]
The UAC2 class handler is identical to the X1700's, shifted by −0x6E4C, literal pools included. Anchors (RAM):

| | X1700 | X1600 |
|---|---|---|
| GET_CUR rate site | `0x0C038ECA` | `0x0C03207E` |
| GET_RANGE clock 6 site / tail | `0x0C038F14` / `F18` | `0x0C0320C8` / `CC` |
| GET_CUR selector site / epilogue | `0x0C038F4C` / `F6E` | `0x0C032100` / `122` |
| reply routine | `0x0C03904A` | `0x0C0321FE` |
| rate getter | `0x0C021C3A` | `0x0C01ED0E` |
| range table (44.1k block) | `0x0C0C3485` | `0x0C0BAF69` |
| cave: lowercase command table (155 B + NUL) | `0x0C0BEA48` | `0x0C0B926C` |

- Rate getter: the firmware has several getters with the same code that read different settings. The rate one reads settings
  base +0x2C / +0xAA on both models, and the USB code loads it (X1600 `0x0C031DCA`, X1700 `0x0C038C16`).
- The lowercase command table has one reference (pointer array at `0x0C0BAE60`), as on the X1700. It differs from the X1700's
  in one command (`cr` instead of `dp`). The uppercase table is untouched, so the service UART keeps working with uppercase commands.
- `tools/gen_patch002.py --model X1600` checks all of the above in the image before it emits an edit (site code, single-use
  literal slots, getter identity, range block, descriptor, cave references). The cave code is the X1700's byte for byte
  (148 bytes); only the 9 address literals differ.
- `tools/sim_patch002.py --model X1600`: 12/12 pass (rate, range and selector answers at 44.1/48/96 kHz).

## Build
```
python tools/gen_patch002.py --model X1600      # writes patches/x1600/002-usb-real-rate.yaml
python tools/sim_patch002.py --model X1600
python tools/build.py --model X1600 --patches none   # must reproduce the original
python tools/build.py --model X1600                  # firmware/builds/X1600FW-<date>-usb-macos+usb-real-rate.BIN
```
Result with patches 001+002: 179 bytes differ from the original (3 + 172 patch bytes + checksum word), sha256
`c8209396c80fee970bf9692ecf96717ae39c27f54b1567156d369bb533e4d1bd` (the first test image).
With patch 003 as well (current web page): 181 bytes differ, sha256 `ab8e1869bef4e36057d5752f9fcfafadad677e499cb6acd7f9ca2e6f3a883921`.

## Patch 003 (Linux / Akai MPC pitch control) [C for the image, H for the effect on an X1600]
The two CS isochronous endpoint descriptors have bmControls 0x15 as on the X1700 (flash `0xCB191` and `0xCB1C8`, checked in the image). Patch 003
changes them to 0x14. On the X1700 this made Linux/the Akai MPC One open the audio stream (see `usb.md`). Untested on an X1600. [H] The Linux quirk
for the X1600's ID may be hiding the same stall.

## Web page
Published as a separate page, `site/x1600/` (https://whatmeansgithub.github.io/DN-X1700/x1600/), marked as confirmed by one
DN-X1600 owner (the author has no DN-X1600). It uses the same `site/patcher.js` as the X1700 page with its own data (`site/x1600/patches.js`,
generated by `tools/gen_site_data.py`) and gives the same image as `build.py` (checked in `site/test.mjs` and with Denon's
real zip in headless Chrome). `tools/x1700_patcher.py` (the command-line program) stays X1700-only for now.
