# DN-X600 port of the USB fixes

Status 2026-11-06: **patch data built and checked in software; NOT flashed on any X600.**

Legend: [C] = confirmed in the firmware image or Denon's updater (code/data), [H] = hypothesis.

## Image
- Denon's `firmware-dnx600-v1030` package contains `X600FW.BIN`, 2 MiB, sha256
  `d58c122694f03493a7fe7da0ddbc77d63e67a317978d6e42285fff861037b5d8`. Kept locally in `firmware/original/` (never committed).
- [C] Same code base as the X1700/X1600: app mapping flash `0x10000..` <-> RAM `0x0C000000..`, USB ID `154E:500F`, service monitor
  ("Hello !!! (DN-X600 monitor)"). The 385-byte configuration descriptor (flash `0xBDACC`) is byte-identical to the X1700's.
- [C] Unlike the other two models there is **no USB-A port and no Utility menu**: the image contains no menu strings and no "PC/MAC" string. The PC/Mac choice is a front-panel key combination (below).

## Update path and integrity rule [C]
- Updates go over USB-B with Denon's **DDJ Updater 2.0.0** (hold Ducking+Select at power-on, drag `X600FW.BIN` into the app, Load, Execute).
  The updater is a generic multi-model JUCE program that talks HID (`DNHID_DeviceNotification`).
- Its file check (ddj_updater.exe, validator at `0x4075B0`) reads a 32-byte trailer at the end of the file:
  `name[0x11]`, `u8`, `u16 VID 0x154E`, `u16 PID`, `u16 version`, `u32 size`, `u32 CRC`, all multi-byte fields big-endian.
  Errors it can raise: invalid file size (size field != real size), CRC error, invalid file format, "update file does not match the device".
- **CRC rule: standard CRC-32 (zlib: init 0xFFFFFFFF, reflected, final xor 0xFFFFFFFF) over `image[:-4]` followed by four zero bytes; the result is stored big-endian in the last 4 bytes.**
  Reproduces the stock image's `A8F51481` exactly. `tools/checksum.py` implements it (`crc32` rule); `tools/models.py` selects it per model.
- Not the X1700 rule (little-endian word sum). The web patcher and `site/test.mjs` still only know the X1700 rule.

## Patch 001 (descriptors)
- Same three bytes as the X1700 at `0xBDAD9`, `0xBDB58`, `0xBDB8F` (`patches/x600/001-usb-macos.yaml`).
- **Mode selection [C from the manual, C for the code path, H for which choice is Mac].** Owner's manual ("Computer OS settings"): the default is
  PC; hold **EFX CUE** and press **BEAT ◂▸** to enter the OS setting mode, choose Windows or Mac with BEAT ◂▸, press **TAP** to enter (SEND/RETURN
  cancels). It cannot be changed while a computer is connected, and a **power cycle is needed** before the descriptors change (confirmed by an owner).
  In the firmware the runtime descriptor rewrite (RAM `0x0C0325E4`, same logic as the X1700's) sets the IAD class to 0x01 and the endpoint sync
  types to 0x0D only when the mode byte at RAM `0x0C51569C` is 1; otherwise it writes 0xFF/0x09. The OS-setting handler (RAM `0x0C034690`) calls
  `0x0C03405C` (which stores the mode through `0x0C032A54`) with **1 for selection 1 and 2 for selection 0**. With the manual's order
  (Windows first, Mac second) that gives Mac = 1 = audio-class descriptors, Windows = 2 = vendor class, the same meaning as the X1700.
  So patch 001's IAD byte is only visible in Mac mode, exactly as on the X1700: **a Mac user must select Mac OS as above.**
  The Windows-first ordering is inferred from the manual's figure text and is not verified on hardware.
- The two `bmControls` bytes are not touched by the rewrite.

## Service manual facts (DN-X600 service manual, 104 pages) [C]
- MCU is the **R5S72630P200FP (SH7263)**, flash **IC103 EN29LV160BB-70TIP (2 MB)**, SDRAM 8 MB: the same CPU family and chip as the X1600.
  The manual's rework table says a flash that already holds software normally needs no programming; an **empty** flash must be written
  with the update/writing procedure, so a bricked unit needs an external programmer (the SH7263 has no mask ROM).
- Update mode: power on while holding buttons 2+3 (Ducking + Select). Panel shows **UP**, USB indicator blue; Windows may ask to install
  a driver from the unit. DDJ Updater (Windows MSI or Mac app): File > Open, Load, Execute. Success shows **donE** on the unit;
  failure shows **FAIL** (unit side) or "Version up was not completed" (PC side).
- Service mode: power on while holding buttons 1+4, EFX selector on REVERB, press TAP: shows `_SYS`, the system version, `_dSP`, the DSP version
  every second. A tester can use this to confirm they run v1.030 before and after the flash. Other service tests useful to testers:
  **USB MIDI OUT test** (selector FILTER: sends test messages such as EfxSnd1, Ch1 Cue, Beat Up, Efx Tap to the host) and a ROM/RAM access test.

## Updater protocol (read from DDJ Updater 2.0.0 with REA/Ghidra; NOT yet seen on the wire)
Why: Denon's Mac `DDJ Updater.app` is a PowerPC + i386 binary that current macOS (27) refuses to launch, and the Windows updater needs a Windows PC.
`site/dnflash.js` re-implements the transfer with WebHID so Chrome or Edge on macOS or Windows can do it; tests: `node site/test_flash.mjs`
(a simulated mixer that checks every byte), plus a dry-run mode in the page. Facts below are [C] = read from the updater's code, nothing yet confirmed on a unit:
- Transport: plain HID (`HID.DLL`, `WriteFile`/`ReadFile` with overlapped waits), **report ID 0, 32-byte reports** in both directions. No feature reports.
- Packet: `byte0 = 0xFF`; `byte1 = 0xF0 | flag<<3 | type` (flag is 1 in every update message); `byte2 = command`; bytes 3..31 payload (29 bytes, zero padded).
- Reply: ACK = flag 1, type 3, command `0x06`; NAK = command `0x15`.
- Sequence (classes `dnhid::VerUp*Message`, threads `UpdateFileLoadThread` = the "Load" button, `UpdateExecThread` = "Execute"):
  1. Select: type 0, command `0x40` -> ACK (retried, 1.5 s apart).
  2. The whole file, header included, in 29-byte blocks, command `0x40`: first block type 4 -> ACK; middle blocks type 5, no reply; last block type 6 -> ACK
     whose bytes 3..4 (big endian) x 1000 give the time Execute may take (15 s if zero). X600 image: 72,316 blocks, the last one 17 bytes.
  3. Exec: type 0, command `0x22` -> ACK within that time (retried twice on timeout), then End Of Transmission: type 3, command `0x04`, no reply.
- Image header (last 32 bytes, big endian): name[17] `DN-X600`, u8 `0x23`, VID `0x154E`, PID `0x500F`, version `0x1030`, size, CRC-32 (rule above).
- [H] Nothing reaches the flash before Exec (Load and Execute are separate buttons), so stopping before Exec is harmless.
- Unknown: the unit's exact USB identity in update mode (the updater only filters on VID `0x154E`; this page does the same), real timing, and whether the
  mixer needs pacing between blocks (Denon's updater does not pace them).
- Suggested first test, in order: dry run; send Denon's **original** file with the browser flasher (changes nothing if it works); then the patched file.
  Cross-check: a USB capture (Wireshark + USBPcap) of one real DDJ Updater run should show exactly these packets.
